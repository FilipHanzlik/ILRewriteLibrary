3. Cecil concepts explained (exposure, not mastery)
--------------------------------------------------
Object hierarchy:
  AssemblyDefinition -> ModuleDefinition -> TypeDefinition
    -> methods, fields, properties, events, nested types, attributes
    -> MethodDefinition.Body -> instructions, locals, exception handlers.

Specific concepts covered:
- Assembly identity properties are inherited by AssemblyNameDefinition from
  AssemblyNameReference.
- A module is not a referenced assembly. MainModule is the normal starting point
  for the sample. module.Types is top-level only; GetTypes() includes nested types.
- Metadata tokens identify table/row pairs within a module, not byte addresses
  or globally unique identities. They can be reassigned during rewriting.
  Newly constructed definitions need not have an assigned output row yet.
- TypeDefinition aggregates relationships across many metadata tables; it is not
  a literal representation of the six TypeDef columns.
- Numerous IsPublic/IsAbstract/etc. properties inspect one flags field rather
  than storing individual Boolean fields.
- Deferred property access can materialize objects and cache them. HasMethods
  can inspect a stored ownership range without creating MethodDefinition objects.
- Mixin is an internal static partial helper class, with ordinary static helpers
  and extension methods; it is not a special C# or metadata concept.
- Collection hooks such as OnAdd/OnRemove are overridable methods called during
  collection operations, not events. Specialized collections maintain ownership.
- Definition classes inherit from corresponding reference classes. A reference
  is not necessarily external.
- Resolve attempts to find a definition. ImportReference produces a suitable
  destination-module reference; it does not copy an implementation.
- Read/modify/write uses one mutable object model. Automatic bookkeeping comes
  from setters, collection hooks, shared object references, and writer logic.
- A call operand may share a MethodDefinition object; not all independently
  represented references, external callers, or reflection names update magically.
- Write success is not semantic validation. Deletion, signature edits, branches,
  EH boundaries, stack correctness, and external consumers remain concerns.
- Properties have accessor methods; fields are separate storage definitions.
  Auto-properties commonly have a property row, accessor methods, and backing
  field. Removing a property alone does not remove all those other entities.
- Custom attributes are separate applications owned by their targets. Two methods
  with ExplorationAttribute have separate CustomAttribute entries/objects.
  Removing one application does not delete the attribute class or another use.
- Less common responsibilities were introduced: resources, interop/marshaling,
  layouts, FieldRVA data, type forwarding, MethodImpl mappings, identity, signing,
  entry points, and debug symbols. These were overview-level explanations only.
- Debug symbols/PDBs were introduced as source/IL sequence-point mappings, local
  names/scopes, and compiler-generated debugging information. The user asked what
  they were; do not assume proficiency with symbol formats or preservation.
- For each feature, distinguish editing support, correct preservation, and
  explicit input rejection.

  var calculator = assembly.MainModule.GetTypes()
      .Single(type => type.Name == "Calculator");
  var add = calculator.Methods.Single(method => method.Name == "Add");
  var attribute = add.CustomAttributes
      .Single(a => a.AttributeType.Name == "ExplorationAttribute");

5. Performance and concurrency discussion
-----------------------------------------
The 20-30 MB limit weakens "too large to fit in memory" as a central argument.
Buffering compact input bytes is different from materializing an object graph.
Object counts, instruction density, resources, repeated/batch processing, edit
density, and analysis costs matter more than size alone.

No speedup or graph-expansion multiplier was established. Cecil already uses
deferred reading and can patch some unresolved bodies without instruction graphs.
Do not compare against an artificially eager or needlessly serialized baseline.

Concurrency is an additional hypothesis, not a completed design:
- A globally locked graph may be safe but serial.
- Fine-grained locks do not by themselves ensure a valid combined transformation.
- Proposed direction: immutable shared input; worker-owned transformations/edit
  plans or method graphs; coordinated conflict handling and token assignment;
  potentially parallel body encoding into independent buffers afterwards.
- Dense edits need not require a single shared mutable graph. Processing methods
  in batches can bound transient memory.
- Independent expensive per-method transformations are more promising than tiny
  flag/attribute edits. Global reachability/deletion is harder to coordinate.
- Allocation, GC, memory bandwidth, load imbalance, and output costs limit gains.
  Parallel workers can increase peak memory.
- Distinguish inter-assembly from intra-assembly concurrency and compare fairly
  against existing parallel processing of independent assemblies.
- SRM does not automatically provide a thread-safe mutable writer architecture.

An illustrative Amdahl calculation used 80% parallelizable work and four workers
to obtain an ideal 2.5x ceiling. Those percentages were hypothetical, NOT measured
and NOT a prediction for this project.

6. Evidence-first profiling proposal (not yet carried out)
----------------------------------------------------------
The user proposed forking/instrumenting Cecil and running actual use cases to
learn timing, allocations, and call counts. This was endorsed with qualifications:

1. Establish an unmodified profiler baseline on real transformations.
2. Instrument meaningful boundaries in a compatible fork:
   - materialized definitions/attributes/instructions;
   - decoded body count and IL bytes;
   - deferred reads and resolution/cache activity;
   - raw-body versus instruction-based writing paths;
   - phase timings and contention.
3. Substitute the fork in the existing tool without changing its algorithm and
   ensure the process actually loads it.
4. Form a bottleneck hypothesis, prototype an optimization, compare equivalent
   outputs and end-to-end performance.

Measure elapsed and CPU time, total allocated bytes, GC, and peak/retained memory
as distinct quantities. Sampling is not exact call counting. Avoid timing every
tiny getter, per-operation logging, contended counters, and summing overlapping
inclusive times. Keep unmodified runs as the reference.
