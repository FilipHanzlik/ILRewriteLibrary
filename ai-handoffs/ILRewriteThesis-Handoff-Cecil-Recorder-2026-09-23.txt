5. ARCHITECTURE: COMPILE, WEAVE, ACTIVATE, ANALYZE
------------------------------------------------
All implementation was written in C#. The tool does not merely emit a mysterious
prebuilt DLL. Cecil is used to rewrite another compiled copy of Cecil.

Four distinct stages:
  A. Compile core with CecilTraceSupport=true.
     Recorder source becomes part of Mono.Cecil.dll, but original method bodies
     still do not call it.
  B. Run the weaver on that diagnostic DLL.
     The weaver inserts IL calls to the recorder's hook API.
  C. Run a consumer that actually loads the woven DLL, with CECIL_TRACE_FILE set.
     The recorder emits the trace as the consumer executes.
  D. Run the separate analyzer over the completed JSONL file.

The recorder is a library hook API, NOT an executable entry point. Its central
public methods are:
  bool IsEnabled { get; }
  TraceCall Enter(RuntimeMethodHandle method, RuntimeTypeHandle declaringType,
                  object target, object[] arguments)
  void Complete(TraceCall call, object target, object result, object[] arguments)
  void Fail(TraceCall call, Exception exception)
  object Unavailable(string reason)
  void Flush()

TraceCall exposes Origin and CallId.

The weaver does NOT inject the recorder implementation itself. Core input must
already contain the compiled hook and marker types. Just running this weaver
against a random original Cecil DLL is insufficient.

CLI:
  Cecil.Trace.Weaver <input.dll> <output.dll>
      [--key <cecil.snk>] [--core <diagnostic Mono.Cecil.dll>]

--key:
  Matching strong-name signing key for signed input. It is not encryption,
  not an Authenticode certificate, and not a source-code access key.
  The output's public-key identity is checked.

--core:
  Diagnostic core used when weaving a companion assembly.
  Supplies recorder references and must have matching assembly identity.
  May be a compatible woven or unwoven diagnostic core.
  It does not copy/instrument core automatically and is not a .NET runtime path.
  The calculator uses core only, so its recorded run did not need --core.

Supported target assembly simple names:
  Mono.Cecil
  Mono.Cecil.Rocks
  Mono.Cecil.Pdb
  Mono.Cecil.Mdb

These names are guards, not proof that all versions/forks are compatible.

Weaver design:
  - Reads assembly metadata/IL using Cecil, not CLR execution of the target.
  - Uses a resolver to find referenced assemblies. This is not NuGet restore.
  - InMemory reading copies input bytes and releases the original file stream;
    it does not mean every body is eagerly decoded.
  - Requests symbols with DefaultSymbolReaderProvider(false). False means
    throwIfNoSymbol=false, not "disable symbols"; subsequent guards reject
    advertised symbols that could not be loaded.
  - Enumerates nested types and all eligible methods, including private helpers,
    accessors and compiler-generated methods. Visibility only gates the exposed
    field inventory; it does not restrict method weaving.
  - Guards entry with IsEnabled before creating argument captures.
  - Uses runtime method/type handles for exact method and generic context.
  - Marks woven methods NoInlining and removes AggressiveInlining.
  - Routes returns to completion logic and records escaping exceptions before
    rethrowing the original exception.
  - Handles generic self references, structs, short branches, existing exception
    handlers, and constructors after base/this initialization.
  - Excludes the diagnostics namespace to prevent recorder recursion.

Explicit rejection/skip boundaries:
  - Unsupported assembly name or managed multi-module target assembly.
  - Already-applied instrumentation marker.
  - Existing output or same input/output path.
  - Missing required matching signing key.
  - Unsupported loaded debug-symbol format or advertised but unavailable symbols.
  - No managed body, diagnostics implementation, varargs, managed-reference
    returns, tail/jmp patterns, unrecognized constructor-initializer patterns.
  - Unsupported values can be marked as capture gaps even when the method itself
    can still be instrumented.

Multi-module restriction applies to the Cecil DLL BEING WOVEN. It does not say
that an application processed later by Cecil can contain only one DLL.
Several DLLs normally mean several assemblies; a WebAssembly module is a
different concept from a managed multi-module assembly.

Portable and embedded portable PDBs are rewritten to embedded portable PDBs.
The named-symbol-provider adapter is needed when staging PE output in memory:
the symbol writer still needs the intended file name.

Outputs:
  A separate instrumented DLL.
  <output.dll>.coverage.json containing method status/reasons, value gaps and
  exposed field declarations. This is STATIC coverage, not runtime frequency.

Weave once per prepared binary and reuse that DLL across workloads. A different
build/version needs its own preparation and validation. Re-weaving an already
woven DLL is rejected.


6. CALL ORIGIN AND CLASSIFICATION: PRECISE MEANING
------------------------------------------------
Origin is PER INVOCATION, not a permanent property of a method and not public
versus private visibility.

The entry hook obtains the immediate caller through:
  new StackFrame(2, false).GetMethod()

It records:
  internal: caller belongs to the executing core Cecil assembly or the recognized
            Rocks/Pdb/Mdb family.
  external: immediate managed caller is outside that family.
  unknown:  caller frame could not be determined.

NoInlining is important to retain the woven method/hook frames. It cannot
prevent every ambiguity from uninstrumented caller inlining, tail calls or
runtime-generated transitions.

caller records assembly, declaring type and method.
parentCallId separately records the enclosing observed Cecil call.
The thread-local nesting stack does NOT determine origin.

Consequences:
  - The same API can be external in one invocation and internal in another.
  - External callback re-entry can have a non-null parentCallId.
  - Framework algorithms calling Cecil comparers/hash methods count as external.
  - LINQ enumerating Cecil collections also produces external calls.
  - Runtime type initializers are marked as runtime work, not replay requests.
  - Never blindly replay every external record independently.

Classification is heuristic-v1:
  read         Getters, inspection/enumeration, read-shaped APIs.
  write        Setters and recognized collection/IL mutations.
  create       Constructors and factory-shaped methods.
  materialize  Recognized decoding operations.
  resolve      Resolution/import-shaped operations.
  emit         Assembly/module/writer output operations.
  lifetime     Disposal/close/finalization.
  other        No recognized classification rule.

These are logical CALL SHAPES, not individual memory reads/writes or proof of
purity. A getter can resolve, decode, allocate or mutate a cache. Emit can touch
many objects. The ratio excludes create/resolve/materialize/emit/etc.; report
these alongside the ratio. Zero writes gives a null ratio, not infinity.

IMPORTANT NEW OBSERVATION FROM THE CALCULATOR RUN:
  Reported external calls: 1,410
    CecilCalculatorDemo immediate callers, including predicates:     69
    System.Linq enumeration:                                        75
    System.Private.CoreLib runtime/framework callbacks:           1,266

All 1,266 CoreLib callbacks had an enclosing observed Cecil call. This includes
type initialization and collection equality/hash callbacks during Cecil work.

For the 69 demo-assembly callers alone, categories were:
  read 44, write 9, create 5, other 9, emit 1, lifetime 1.

Thus the report's external read/write ratio is NOT automatically the ratio of
explicit demo/ILLink requests. Filtering only to the demo caller is a different
metric and also omits LINQ calls made on its behalf. Caller/ancestry-aware logical
boundary aggregation remains future work. The source of a call is available in
the raw log; do not flatten this distinction away in thesis conclusions.


7. RECORDER LIFETIME, SAFETY AND JSONL SCHEMA
-------------------------------------------
Activation:
  CECIL_TRACE_FILE must be set before starting the consumer.
  The consumer must actually load the woven Cecil DLL.
  The output directory must already exist.
  {pid} in the filename is replaced by the process ID.

No variable => recording disabled. Woven-but-disabled IL still differs from an
unmodified build, including inlining/EH behavior; it is not a pristine
performance baseline.

Configuration is read on first use. Mid-run toggling is not supported.
The recorder is a lazy singleton PER LOADED CORE ASSEMBLY, shared by the
companions and threads using that core. It is not one magical global writer
across all AssemblyLoadContexts/processes.

Use one instrumented Cecil load context per process and unique output filenames.
The file is opened with CreateNew: no overwrite or append. A second writer using
the same file fails explicitly.

A global lock serializes complete records and assigns sequence numbers.
A thread-static current-call stack tracks nesting.
A thread-static capture guard suppresses recorder-induced recursive tracing.
The writer flushes each record. Recording failures propagate; they do not
silently turn into successful runs with missing data.

Schema version: 1
Each record is one JSON line. Main events:
  session
    Schema, process/runtime, actual loaded core path/SHA256/MVID, limits,
    timestamp frequency, byte order and global limitations.
  method
    Method ID, type/assembly/MVID/token, signature/overload, parameters and
    directions, generic arguments, constructor/type-initializer flags, category.
  enter
    Sequence, callId, methodId, parentCallId, threadId, depth, origin, caller,
    receiver, arguments, replay issues and optional observations.
  leave
    Matching callId/thread, returned/threw, inclusive elapsed ticks, result and
    post-call captures on success; exception information/state gap on failure.
  shutdown-start
    Process-exit notification and open/total counts.
  shutdown-continued
    Reopens a prior shutdown checkpoint when later exit handlers call Cecil.
  session-end
    Total calls, open calls, recorderFailed and shutdown-checkpoint information.

callId is the sequence number of its enter record. Method descriptors and other
events also consume sequence numbers. Pair by IDs/thread/parents, not adjacent
lines. A void result is represented as unavailable with reason "void"; it is not
an unexpectedly missing return value.

Important shutdown fix:
Do not close the recorder inside its ProcessExit callback. Other exit handlers
may still use Cecil. The current implementation leaves the process-lifetime
AutoFlush stream usable, writes clean checkpoints when no calls remain, and
lets the OS close it at termination. Later calls use shutdown-continued and a
new checkpoint. The final record must be a clean session-end.

The analyzer streams records, retaining descriptors, counters, active stacks and
bounded issue examples, not the whole object history. It checks sequences,
descriptors, nesting, argument counts, statuses, snapshot shapes, producer
temporal ordering and the final checkpoint. It supports the earlier schema-1
single-terminal-end form too.

An important temporal-validation fix:
A nested call can enter after its parent and return an object used in the
parent's leave snapshot. Validate producer timing against the SNAPSHOT sequence,
not only the parent's entry call ID.

Special body observations, obtained without invoking getters:
  MethodDefinition.get_Body entry:
    bodyWasCachedAtEntry, bodyRvaAtEntry.
  Successful CodeReader.ReadMethodBody(MethodDefinition) completion:
    materializationCompleted, declaredIlBytes, decodedInstructionCount.

These count completed decoding EVENTS, not necessarily distinct bodies.
A cache miss is not itself proof that decoding occurred. The private helper
overload is not counted a second time.

Elapsed ticks include instrumentation and nested work. Do not sum all inclusive
times as independent costs or treat them as uninstrumented performance data.


8. VALUE CAPTURE, OBJECT IDENTITY AND RECONSTRUCTION
---------------------------------------------------
The original wish to construct a fresh argument object for every call is not
generally sound. Cecil node identity matters for collections, instruction
removal, shared branch targets, attached definitions and resolution.

Snapshots distinguish:
  value
    Null, scalars, strings, enums and supported immutable/reflection values.
  snapshot
    Arrays/bytes, struct fields and known reader/writer/module option objects.
  reference
    Previously produced object with id, sourceCallId and sourcePath.
  unavailable
    Explicit reason requiring a driver/adapter, preserved input or more data.

Do not assume all scalar JSON values are numbers: integers may be represented
as strings to preserve exact values. Respect the recorded type/encoding.
Float/double bits are preserved in base64; decimal preserves component integers.
Strings with lone UTF-16 surrogates use utf16le-base64 rather than lossy JSON.

Objects have weak identities through ConditionalWeakTable; observing an object
does not retain it strongly. Repeated occurrences of an ID must map to the same
reconstructed object when requiresIdentity=true.

External constructors, successful return values and ref/out results establish
producer recipes. Paths include:
  receiver
  result
  arguments[index]
  array coordinates, including non-zero lower bounds/multiple dimensions
  .field(percent-encoded-declaring-type,percent-encoded-field-name)

Field path segments use Uri.EscapeDataString and name real fields, not getters.
sameSnapshot references preserve cycles/aliases. Value-type receivers include
their field state after successful calls. External derived objects are not
treated as constructible just because their Cecil base constructor was seen.

Snapshots use fields rather than arbitrary Cecil getters or ToString, avoiding
lazy materialization and other observer-induced behavior.
Array rank, dimensions, lower bounds, aliases and cycles are represented.
Unsupported/truncated mutable arrays must stay explicitly unavailable even if
they have an object producer; a producer is not a complete content snapshot.

Limits, all requiring positive integer values:
  CECIL_TRACE_MAX_DEPTH   = 6
  CECIL_TRACE_MAX_ITEMS   = 256
  CECIL_TRACE_MAX_BYTES   = 65536
  CECIL_TRACE_MAX_STRING  = 16384 UTF-16 code units

Exceeding a limit is marked unavailable, not silently truncated or replaced with
a success-shaped placeholder.

Streams, delegates, custom resolvers/services, native pointers, dynamic
reflection values and unproduced opaque objects may require adapters.
Internally created objects often lack an EXTERNAL producer; that warning does
not mean they must all be created individually by a logical external replay.

Input filenames are recorded, but file contents, symbols and dependencies are
NOT automatically bundled into the trace. Preserve an input bundle separately.
Output paths need remapping during replay. An externally supplied FileStream is
explicitly unavailable as a self-contained replay recipe.

Reference copies, reference-equality tests, consumer locals, external array
writes and external services are not recorded. Obtaining an object through an
instrumented API is visible; simply copying its reference is not.

There is a tested BOUNDED reconstruction example for instruction/collection
operations, values and identity. There is NO general replay CLI, automatic LLM
replay generator or proof of arbitrary-workload reproducibility.

13. LIMITATIONS AND MISSING FEATURES
------------------------------------
Observation/replay boundaries:
  - Only woven managed method bodies are intercepted.
  - No complete field-access, reference-copy, reference-equality or memory trace.
  - No interception of arbitrary external array/collection/service mutations.
  - Input files/symbols/dependencies must be preserved outside the log.
  - Streams, delegates, external subclasses/resolvers and opaque values may need
    explicit driver/adapters.
  - Unsupported pointer/typed-reference/byref-like values are explicit gaps.
  - Ref/out VALUES are captured, but their storage locations and aliases are not.
  - Ref/out/receiver post-state after an exception is not captured.
  - Derived constructor entry is after base/this initialization. Initializer
    work may lack the later derived-constructor parent; failures before entry
    have no derived entry.
  - Runtime type initialization is not an independent consumer replay request.
  - Global sequence is recorder-observation order, not a deterministic scheduler.
  - Logical origin can be obscured by framework bridges or uninstrumented frames.
  - Snapshot limits can make otherwise supported data unavailable.
  - Analyzer temporal/reference checks are not a full reconstructed-graph proof.
  - NativeAOT/trimming of the diagnostic reflection runtime is not supported.
  - A process crash/kill or logging failure can leave an incomplete trace.

Performance/storage:
  - Every eligible internal call is observed.
  - Caller stack inspection, disabled inlining, allocations/boxing, reflection
    snapshots, synchronized JSON output and per-record flushes are expensive.
  - Full traces are large even for tiny samples: this calculator produced 95.8 MB.
  - No event/file-size budget, graceful budget-exhausted marker, counters-only
    mode, external-only mode, sampling or optimized buffered output is implemented.
  - Do not start unrestricted production-scale ILLink recording without a bounded
    pilot, space planning and an agreed experiment scope.
  - No measured general slowdown factor is available.
  - Use an UNINSTRUMENTED same-source/toolchain build for timing/allocation/GC
    baselines, not a woven-but-disabled DLL.

Security/handling:
  - Logs contain paths, metadata names, arguments, resources and option fields,
    potentially including signing-related data. Treat them as sensitive.
  - Do not upload traces/source to third-party services without authorization.
  - Do not replace shared NuGet or installed SDK files for an experiment.
  - Keep source input, original core, diagnostic unwoven core, woven core and
    rewritten application output distinct.

Functional work still missing:
  - General reconstruction/replay driver and workload-specific adapters.
  - Automated preserved-input/environment/dependency bundle.
  - Logical consumer-boundary/caller-aware aggregation in the analyzer UI/report.
  - Consumer/native/field instruction instrumentation.
  - Bounded production recording and lower-overhead modes.
  - Real ILLink/Blazor or macios integration, compatibility validation and baseline.
  - Validation across different dotnet/cecil or upstream Cecil revisions.
  - Packaging/versioned distribution/CI integration for this tooling.

Do not present any item in this list as already implemented.

15. PORTING TO ANOTHER CECIL VERSION AND NEXT WORK
------------------------------------------------
For a fresh Cecil source tree:
  1. Identify exact fork/revision, consumer dependency and signing identity.
  2. Preserve an ordinary unmodified baseline using that source/toolchain.
  3. Integrate the diagnostics source and optional compile wiring into core.
  4. Check private-field/body-observation/snapshot assumptions against that version.
  5. Build diagnostic core; adapt and build the weaver if needed.
  6. Weave separate supported DLLs with matching key/core identity.
  7. Review all skipped methods, value gaps and exposed fields.
  8. Validate symbols, signatures, output behavior, disabled/enabled tracing and
     log semantics on bounded examples before substituting into a real consumer.

The current assembly-name allow-list does not certify arbitrary versions.
Older/newer APIs, runtime targets, metadata patterns and private field layouts
can require adaptation. Upstream Cecil and dotnet/cecil share many names but are
not interchangeable experimental baselines.

Potential next tasks, to choose with the user:
  - Add persistent semantic-regression assertions for the calculator recording.
  - Define/report logical consumer operations separately from immediate-caller
    origin, with a deliberate policy for LINQ and framework callbacks.
  - Implement a recording budget and explicit incomplete/budget-exhausted status.
  - Design adapters for the actual consumer's streams/resolvers/callbacks.
  - Build a compatible isolated ILLink/Blazor experiment with preserved inputs
    and a new uninstrumented baseline, then perform a small recording pilot.
  - Only then scale up and use observations to form an SRM-library hypothesis.

For a replay effort, start with a bounded contract rather than replaying all
33,412 calls. Re-executing one high-level request already regenerates internal
work, and framework callbacks/type initializers need special handling.
