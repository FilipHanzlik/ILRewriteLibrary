3. Topics explained or explicitly acknowledged
----------------------------------------------
Reading mechanics:
- FileStream -> PEReader -> MetadataReader.
- using declaration disposes on scope exit, not at last use; disposal is not GC.
- FileAccess vs FileShare; FileShare.ReadWrite allows modification and is not a
  snapshot guarantee. FileShare.Read was recommended for the Windows exercise.
- Default lazy/block reading vs PrefetchMetadata vs PrefetchEntireImage.
- Full input byte buffering is not full object-graph construction.
- Keep backing memory stable/alive, and do not dispose while workers read.
- Full-image prefetch is a reasonable configurable prototype policy for rewriting,
  not a measured fastest setting or a concurrency solution.

Metadata:
- TypeDefinitions enumerates TypeDefinitionHandles, including nested types.
- Handles identify rows; GetTypeDefinition returns a lightweight reader/row view;
  property access reads columns; GetString decodes heap text.
- Metadata is available in memory, not fetched by a disk read per getter.
- StringHandle is a locator, not a C# string, global ID, or pointer.
- reader.StringComparer.Equals(handle, text) avoids intermediate decoded strings.
- IsNil is a property; table row zero means no entity, not comprehensive validity.
- EntityHandle.Kind discriminates table kinds; permitted kinds depend on context.
- GetAssemblyDefinition, Name vs GetAssemblyName/GetAssemblyNameInfo.
- Assembly version is four numeric fields, not a string-heap entry.
- Table/heap getters; BlobReader vs copying blob bytes.
- TypeDef.MethodList ownership ranges; GetDeclaringType is a metadata lookup.
  Avoid rediscovering an owner already known in the traversal, but do not assume
  this is a material bottleneck or immediately add caches.
- Method/field flags vs custom attributes.

Bodies and references:
- RVA -> MethodBodyBlock; MaxStack is a limit (tiny header implies 8).
- Locals vs parameters vs evaluation stack; source locals may be optimized away.
- AsSpan on ImmutableArray adds no array copy. This does not establish that
  GetILContent itself is a zero-copy operation.
- MethodDef vs MemberRef, external TypeRef/AssemblyRef chains, MethodSpec.
- Attribute applications refer to constructors; constructor declaring type gives
  attribute type name. Constructor is MethodDef or MemberRef, not arbitrary kind.
- SRM reads attributes without instantiation; runtime reflection requesting
  actual instances can execute constructors and named-argument setters.

6. Essential performance corrections to preserve
------------------------------------------------
The assistant initially described compact row structs as an SRM speed advantage.
Source inspection then showed Cecil's final writer already uses arrays of row
structs. This was explicitly corrected; do not repeat the simplistic comparison.

Cecil writing:
- Normally rebuilds a complete output image, not a delta file.
- Builds metadata rows/heaps and method bodies, then emits the PE.
- Has an unresolved/raw-body patching path as well as instruction-based emission.
- Broad metadata materialization is not synonymous with decoding every IL body.
- Can write different assemblies concurrently with independent mutable graphs,
  services, and output destinations. This is not a new SRM capability.
- Shared resolver caches can cause otherwise separate jobs to share objects.

SRM:
- Compact row lists and chunked BlobBuilder buffers are concrete implementation
  mechanisms, not an end-to-end speedup benchmark.
- Retaining a Cecil-like graph and replacing only the emitter may be faster,
  equivalent, or slower; translation and required work must be counted.
- Do not omit stack work, deduplication, symbols, signing, or preservation and
  describe the result as equivalent faster emission.
- Total gains depend on the actual dominant phase. No minimum gain is justified.

Remaining hypotheses: avoid unnecessary materialization/decoding, repeated
resolution, or parallelize expensive independent intra-assembly processing.
None is demonstrated for the user's actual tool.

7. Thread-safety discussion and evidence level
---------------------------------------------
The user specifically challenged "SRM is absolutely thread-safe."
That blanket statement is false/too broad and was corrected.

- PEReader explicitly supports parallel reading, excluding concurrent disposal.
- Metadata views require stable backing memory/lifetime; custom decoders/providers
  and mutable cursors have their own requirements.
- A shared MetadataBuilder is not safe for unsynchronized mutation.
- A shared BlobBuilder is not safe for unsynchronized appends.
- Worker-local builders can be used independently; combination requires planning.
- Thread safety is not parallel speedup; a global lock serializes work.
- Individually safe edits do not guarantee a semantically valid combined result.

Evidence for MetadataBuilder is implementation-based, not an explicit statement
found on its API page:
  _methodDefTable is a List<MethodRow>.
  AddMethodDefinition does List.Add(...) then derives the result from List.Count
  with no synchronization. There is both list mutation risk and an add/count race.
  List<T> documentation requires synchronization for concurrent read/write use.

Potential architecture, NOT settled:
  Stable input -> worker-owned transformations -> coordinated handles/conflicts
  -> independent body encoding where feasible -> coordinated metadata/final output.

No concurrency prototype or throughput measurement exists.
