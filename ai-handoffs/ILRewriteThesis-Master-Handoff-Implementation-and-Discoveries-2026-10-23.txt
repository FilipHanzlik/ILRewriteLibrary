2. SRMREWRITE CORE ARCHITECTURE & DESIGN PHILOSOPHY
=======================================================================
The architecture avoids Mono.Cecil's fatal bottleneck: allocating an entire object graph
(TypeDefinition, MethodDefinition, Instruction, ParameterDefinition) for every entity in
an assembly. Instead, `SrmRewrite` decouples original immutable data from mutations.

2.1 AssemblyRewriteContext (Unmanaged Lifecycle & Zero-GC Ingestion)
- File: `proof-of-concept-il-rewrite/AssemblyRewriteContext.cs`
- Ingestion is executed via `File.OpenHandle` and `RandomAccess.Read` directly into unmanaged
  memory allocated with `NativeMemory.Alloc((nuint)size)`.
- Rationale:
  * An assembly image (up to multiple megabytes) read into a managed `byte[]` would immediately
    land in the Large Object Heap (LOH, objects >= 85,000 bytes).
  * LOH allocations are rarely compacted and trigger expensive Gen 2 garbage collections.
  * Native allocation guarantees ZERO managed heap pressure during ingestion.
- The context wraps the memory in a `PEReader` and constructs the coordinated triad:
  `MetadataReader` -> `MetadataEditor` -> `OverlayReader` -> `PeWriter`.
- Implements `IDisposable` with deterministic release via `NativeMemory.Free`.

2.2 OverlayReader & Tiered Query Model
- File: `proof-of-concept-il-rewrite/OverlayReader.cs`
- Implements a read-only, real-time merged view of original metadata and recorded mutations.
- Exposes two query tiers:
  * Tier 1 (High-Level SRM entities): `OverlayMethodDefinition` wrappers providing
    SRM-like access (`ImplAttributes`, `HasBody`, `GetLogicalILBytes()`, `GetLogicalBodyBlockBytes()`).
  * Tier 2 (Low-Level Bulk Metadata): Exposes direct unmanaged memory pointers
    (`GetRawMetadataSpan()`, `GetTableOffset()`, `GetTableRowSize()`, `GetTableRowCount()`,
    `GetHeapOffset()`, `GetHeapSize()`). Used by `PeWriter` to stream unmodified heaps and
    tables with zero decoding.

2.3 MetadataEditor & MethodDefEditor (Sparse Delta Mutation)
- Files: `proof-of-concept-il-rewrite/MetadataEditor.cs`, `MethodDefEditor.cs`
- Mutations are stored strictly as deltas. Unmodified tables and rows consume zero memory.
- When a method is edited via `context.Editor.Edit(handle)`:
  * Returns a stack-allocated `MethodDefEditor` struct.
  * Mutates an internal flat/sparse `MethodDefOverride[]` array indexed directly by row RID.
  * `MethodDefOverride` is an immutable `readonly struct` storing:
    `IsModified`, `ReplaceWithSharedRet`, `ClearBody`, `ImplAttributesToAdd`, and `CustomBodyBytes`.

2.4 PeWriter (3-Stage Sequential Streaming Container Emission)
- File: `proof-of-concept-il-rewrite/PeWriter.cs`
- Performs deterministic, zero-allocation container synthesis in three stages:

Stage 1: Precompute Section & RVA Layout in `.text`
- Calculates virtual offsets and RVAs for every section component:
  1. IAT (8 bytes) + CorHeader (72 bytes).
  2. Method Bodies: Shared `ret` (`[0x06, 0x2A]`), plus custom or unmodified bodies.
  3. StrongName signature reservation (if present in input).
  4. Debug Directory (CodeView entry pointing to original PDB, reproducible entry).
  5. Metadata Root (`BSJB` header, stream headers, raw metadata tables and heaps).
  6. Managed Manifest Resources (verbatim pass-through from input PE).
  7. Field Data (mapped static fields with relocated FieldRVAs).
  8. Import Table (ILT, Hint/Name `_CorDllMain`/`_CorExeMain`, `mscoree.dll`).
  9. Startup Stub (x86 `jmp [mscoree.dll]` stub).
- Precomputes exact section headers, virtual sizes, and file alignments (512-byte raw, 8192-byte virtual).

Stage 2: In-Place Native Metadata Construction & Table Patching
- Allocates a single native scratch buffer `NativeMemory.Alloc(metadataLength)`.
- Copies the raw input metadata block into the scratch buffer in a single span copy.
- Patches the `MethodDef` table in-place:
  * Writes updated 4-byte `RVA` (offset `+0`).
  * Bitwise-ORs `MethodImplAttributes.NoInlining` and any delta flags into 2-byte `ImplFlags` (offset `+4`).
- Patches the `FieldRVA` table in-place (updates field RVAs by the delta shift).
- Re-sorts `CustomAttribute` rows if legacy custom attribute defect reproduction is active.

Stage 3: Direct Sequential File Emission (Zero Intermediate Copies)
- Streams directly into the destination `FileStream` (with 64 KB buffer):
  * PE Headers (DOS header, PE signature, COFF header, Optional header, Section headers) written from stackalloc buffer.
  * `.text` section content written sequentially.
  * `.reloc` section written (12 bytes base relocation table for startup stub).
  * `.rsrc` section written (verbatim pass-through if present in input PE).

3. THE ARCHITECTURAL HARDENING PATCH
=======================================================================
The codebase was hardened in three critical areas to guarantee encapsulation, eliminate
heuristics, and unlock general-purpose partial assembly rewriting:

3.1 Fix 1: Strict Encapsulation Between PeWriter and MetadataEditor
- Problem: `PeWriter` previously reached directly into `_reader.Editor.MethodDefOverrides`,
  violating the layered architecture where `PeWriter` must only query `OverlayReader`.
- Solution:
  1. Removed `public MetadataEditor Editor` from `OverlayReader.cs`; `_editor` is strictly private.
  2. Made `MethodDefOverride` a `public readonly struct`.
  3. Exposed `_reader.TryGetMethodDefOverride(int rowId, out MethodDefOverride overrideVal)`
     and `_reader.IsTableModified(TableIndex table)` on `OverlayReader`.
  4. `PeWriter` now only depends on `OverlayReader`.

3.2 Fix 2: Exact FieldRVA Sizing via ClassLayout and Blob Signatures
- Problem: The extent of the static field data block in `.text` was approximated using
  `const int maxFieldLen = 256`. If static array initializers exceeded 256 bytes and did
  not sit at the end of the section, data would be truncated.
- Solution: Implemented `GetFieldDataSize(int fieldRowId)` in `PeWriter`:
  * Resolves `fieldRowId` from column `+4` of the `FieldRVA` table (`0x1D`).
  * Inspects `FieldDefinition.Signature` using `BlobReader`.
  * Skips optional (`0x20`) and required (`0x1F`) custom modifiers.
  * For primitive types (`Boolean` through `UInt64`, `IntPtr`), maps to 1, 2, 4, or 8 bytes.
  * For `ValueType` (`0x11` / `TypeHandle`): reads `TypeDefinitionHandle` and checks
    `typeDef.GetLayout().Size` from the `ClassLayout` table (`0x0F`) in O(1) time.
    (Compiler-generated `<PrivateImplementationDetails>` array structs always specify their
    exact byte size in `ClassLayout`).
  * Computes `maxFieldEndRva = Math.Max(maxFieldEndRva, rva + fieldSize)` across all entries.
  * `fieldCopyLen = Math.Min(maxFieldEndRva - minFieldRva, block.Length)`.

3.3 Fix 3: Dual-Path General Method Body Rewriting (Fat/Tiny Alignment & Preservation)
- Problem: Previously, `PeWriter` assumed that every method with a body was stripped to
  `sharedRetRva`. If a user modified only 1 method in an assembly of 1,000 methods, the
  other 999 methods were left with invalid RVAs and missing bodies.
- Solution:
  1. Added `public MethodDefEditor SetRawBody(byte[] rawMethodBodyBytes)` to `MethodDefEditor`.
  2. Added `public byte[]? CustomBodyBytes;` to `MethodDefOverride`.
  3. Updated `OverlayMethodDefinition.GetLogicalBodyBlockBytes()` to return `CustomBodyBytes`
     when present.
  4. In `PeWriter`:
     - Stage 1 detects whether `hasNonStrippedBodies` is true (`CustomBodyBytes != null` or
       unmodified method with `origRva != 0`).
     - Fast Path (`hasNonStrippedBodies == false`): 100% of whole-assembly `ILStrip` runs
       execute the existing zero-allocation fast path without renting any arrays.
     - General Path (`hasNonStrippedBodies == true`):
       * Rents `uint[] newMethodRvas = ArrayPool<uint>.Shared.Rent(methodRowCount + 1)` and
         returns it in the `finally` block.
       * For custom bodies: aligns `curOffset` to 4 bytes if Fat header (`(firstByte & 0x03) == 0x03`),
         records `newMethodRvas[r] = textRva + curOffset`, and advances `curOffset`.
       * For unmodified bodies: retrieves original body size via `peReader.GetMethodBody(origRva).Size`,
         checks first byte of section data for Fat header alignment, records `newMethodRvas[r]`,
         and advances `curOffset`. Deduplicates identical original RVAs.
       * In Stage 2: writes `newMethodRvas[r]` to `MethodDef` row `r`.
       * In Stage 3: emits custom and unmodified method bodies sequentially in the exact same
         order and alignment calculated in Stage 1.

4.3 Why Managed Allocation is ~87 KB for a 2 MB PE File (NativeMemory vs LOH)
A common question arises: "How can the code allocate only 87 KB of managed memory when
processing a 2 MB file? Doesn't it need the image in memory?"

Explanation:
- The entire 2 MB file image IS held in memory, but it lives in UNMANAGED memory via
  `NativeMemory.Alloc`.
- In managed .NET runtimes, any object >= 85,000 bytes is allocated on the Large Object Heap (LOH).
  Mono.Cecil reads assemblies into managed byte arrays, memory streams, and millions of class
  instances (TypeDefinition, MethodDefinition, Instruction, ParameterDefinition). This causes
  86+ MB of heap churn and forces Gen 1 and Gen 2 GC pauses.
- `SrmRewrite` bypasses the managed garbage collector entirely for the raw binary data:
  1. The input PE is mapped via `NativeMemory.Alloc`.
  2. SRM's `PEReader` reads directly from unmanaged pointers (`new PEReader(byte* peImage, int size)`).
  3. The mutable metadata buffer is allocated in native memory (`NativeMemory.Alloc(metadataLength)`).
  4. Heap strings (`#Strings`), blobs (`#Blob`), and resources are copied as raw pointer spans.
  5. The ~87 KB reported by BenchmarkDotNet is purely the ephemeral managed overhead of
     `FileStream`, small CLI string paths, and minimal framework bookkeeping.
  6. The garbage collector never runs: Gen 0 = 0, Gen 1 = 0, Gen 2 = 0.

5. CRITICAL TECHNICAL DISCOVERIES, QUIRKS & SPECIFICATION DEVIATIONS
=======================================================================

5.1 Metadata Stream Ordering: Roslyn vs Mono.Cecil (#US vs #GUID)
During referent validation, an apparent hash mismatch occurred on some assemblies:
`Candidate does not match the legacy whole golden`.
Investigation revealed:
- In Roslyn-compiled assemblies (e.g. `CommunityToolkit.Maui.dll`), metadata streams are
  ordered: `#~`, `#Strings`, `#US`, `#GUID`, `#Blob`.
- Mono.Cecil's metadata writer (`BuildMetadata`) has a hardcoded stream emission sequence:
  `#~`, `#Strings`, `#GUID`, `#Blob`, `#US`.
- When Mono.Cecil strips an assembly, it deserializes and re-serializes every stream, forcing
  them into its own hardcoded order.
- `SrmRewrite` performs true zero-copy pass-through of the `#~` metadata block. It preserves
  the original compiler's stream layout byte-for-byte.
- Invariant Impact:
  * Semantically and structurally, both orderings are 100% compliant with ECMA-335 Partition II.24.
  * `StripReplay.BinaryInspection.VerifyWhole` verifies that all types, methods, tokens, and
    metadata heaps match 100%.
  * However, byte-for-byte `NormalizedSha256` equality is only achievable if streams are
    re-ordered to mimic Mono.Cecil. Preserving Roslyn's original layout is architecturally
    superior because it requires zero re-serialization.

5.2 Legacy Cecil CustomAttribute Defect Replication
Mono.Cecil has a historical bug in its custom attribute parent decoder:
- In ECMA-335 II.22.10, the `HasCustomAttribute` coded index uses 5 tag bits (0 to 21).
- Tags 20 (`GenericParamConstraint`) and 21 (`MethodSpec`) are mishandled by legacy Cecil:
  it loses their parent token and resets the parent to RID 0 (`MethodDef 0`), then re-sorts
  the `CustomAttribute` table.
- To maintain 100% compatibility with the referent oracle validation suite, `PeWriter` includes
  `ReplicateLegacyCustomAttributeBug = true`:
  * Detects custom attributes with parent tag 20 or 21.
  * Zeroes their parent column.
  * Re-sorts the table rows using an unmanaged `CustomAttributeComparer`.

5.3 Method Body Header Alignment: Tiny (1-byte) vs Fat (4-byte) & Exception Tables
When extending `PeWriter` to support general method body preservation (Fix 3):
- ECMA-335 II.25.4 specifies two method body formats:
  * Tiny Format (`(header & 0x03) == 0x02`): Methods < 64 bytes of IL, maxstack <= 8, no locals,
    no SEH. Can be located at any byte boundary (1-byte alignment).
  * Fat Format (`(header & 0x03) == 0x03`): Methods with locals, maxstack > 8, or exception
    handling clauses.
- Critical Invariant: ECMA-335 II.25.4.3 explicitly mandates that Fat method headers MUST
  be aligned to a 4-byte boundary in `.text`.
- If a method body has exception handling sections (`CorILMethod_Sect_EHTable`), they are
  appended after the IL stream and are also aligned to 4 bytes.
- `peReader.GetMethodBody(origRva).Size` accurately computes the complete byte size including
  headers, IL, padding, and all exception tables. Copying `Size` bytes from the section pointer
  preserves the entire method body intact.

5.4 Windows OS I/O Jitter, Page Cache, and Antivirus Impact on Benchmarks
During benchmarking and testing on Windows:
- A stark difference was observed between cold runs (~70-100 ms) and hot in-memory execution (~10 ms).
- Investigation showed that Windows Defender / Antivirus filter drivers intercept file creation
  and closure events (`IRP_MJ_CREATE`, `IRP_MJ_CLEANUP`) when writing to user temp folders.
- Antivirus scanners inspect new executable PE headers synchronously on write completion,
  adding 30-50 ms of artificial I/O latency completely outside the managed runtime.
- For pristine thesis measurements, benchmarks should either:
  1. Add an antivirus process exclusion for the benchmark runner.
  2. Use a RAM disk or execute under Linux, where page cache writebacks are asynchronous.

7. ROADMAP: EXTENDING SRMREWRITE TO GENERAL-PURPOSE IL REWRITING
=======================================================================
With the completion of the Architectural Hardening Patch, `SrmRewrite` is no longer
just an IL stripper—it is a functional partial assembly rewriting engine.

Next Steps for Subsequent Development Phases:
1. Portable PDB Synchronization:
   - When methods are removed, modified, or reordered, synchronize method debug information
     in the associated Portable PDB (`SequencePoints`, `LocalScopes`).
2. Instruction-Level Method Editing:
   - Provide an SRM-based `MethodBodyEditor` for parsing, inserting, and rewriting individual
     CIL instructions (e.g. logging hooks, call redirection) without decoding the entire body.
3. Member Removal (Tree-Shaking):
   - Support marking `TypeDef`, `MethodDef`, or `Field` rows as deleted by compacting metadata
     tables and updating coded index tokens.
