IL REWRITE THESIS - BENCHMARKING & PROFILING STRATEGY
Updated: 2026-10-09
======================================================

Purpose
-------
This document summarizes the current strategy for measuring the performance and memory overhead of Mono.Cecil compared to a System.Reflection.Metadata (SRM) based approach. It outlines the transition from micro-benchmark trace replays to End-to-End (E2E) profiling, and details the exact toolchain used to diagnose Cecil's behavior.

1. The Benchmarking Philosophy
------------------------------
*   **The Micro-Benchmark Trap:** Attempting to replay every individual Cecil property getter and setter in a benchmark is fundamentally flawed. It forces the new SRM library to emulate Cecil's eager object-model API, hiding the true architectural advantages of zero-allocation metadata reading.
*   **The E2E Solution:** Benchmarks must be End-to-End macro-tasks (e.g., "Load this DLL, strip all `[Obsolete]` attributes, write the DLL"). The benchmark acts as a black box around the two different libraries, proving that for the exact same business goal, SRM uses drastically less memory and time.
*   **The Role of Traces:** The 6.4 MB JSONL traces generated by the custom Cecil instrumenter are for *discovery*, not direct code generation. They reveal the logical intent of real-world workloads (like ILLink or Android tasks) so we know which E2E scenarios to build.

2. Diagnostic Toolchain
-----------------------
To get a complete picture of performance, we use three distinct tools, each answering a different question:

1.  **BenchmarkDotNet (BDN):** 
    *   *Answers:* "How much total time and memory?"
    *   *Usage:* E2E test suites with `[MemoryDiagnoser]` to track managed allocations and GC collection counts (Gen0/1/2) for the entire workload.
2.  **dotnet-trace (EventPipeProfiler):**
    *   *Answers:* "When and how long was execution paused?"
    *   *Usage:* Attached to BDN via `[EventPipeProfiler(EventPipeProfile.CpuSampling)]`, or run manually via CLI. It tracks CPU stacks millisecond-by-millisecond.
3.  **SpeedScope (speedscope.app):**
    *   *Answers:* "Where exactly did Cecil waste CPU cycles?"
    *   *Usage:* A visualizer for the `.speedscope.json` files generated by `dotnet-trace`. Allows us to filter for `gc_heap::garbage_collect` or `GC_Heap::Allocate` to visually prove the overhead of Cecil's object graph.

3. Step-by-Step: Capturing and Diagnosing Cecil
-----------------------------------------------
To capture a clean performance profile of Cecil running an analyzer workload, follow these steps:

**Step A: Prevent MSBuild Caching Traps**
MSBuild's timestamp optimization can silently restore uninstrumented or stale versions of `Mono.Cecil.dll` from companion folders (like `recordings/`).
*   *Fix:* Add `<DefaultItemExcludes>$(DefaultItemExcludes);recordings\**</DefaultItemExcludes>` to your `.csproj` to hide backup directories from the build system, or use a raw `<Exec Command="cp -f ...">` MSBuild target to force the overwrite.

**Step B: Capture the Logical Trace (For Scenario Discovery)**
Run the woven Cecil workload with the environment variable to generate the JSONL file.
```bash
CECIL_TRACE_FILE=./trace.jsonl dotnet run -c Release
```
*Note: A 6.4 MB file is expected for a simple run due to object state snapshots and micro-interactions.*

**Step C: Capture the CPU/GC Profile**
Run the workload through the official .NET runtime profiler.
```bash
dotnet tool install --global dotnet-trace
dotnet-trace collect --format speedscope -- dotnet run -c Release
```
This generates a `trace.speedscope.json` file.

**Step D: Analyze the Profile**
1. Drop the `trace.speedscope.json` file into https://www.speedscope.app/
2. Use the **Left Heavy** view.
3. Search for `GC` to see the exact percentage of total execution time stolen by Garbage Collection, directly illustrating the cost of Cecil's eager allocations.

4. Next Implementation Steps (Hybrid Workflow)
----------------------------------------------
To quickly build out the E2E benchmark suite without getting bogged down by LLM context limits on massive JSON files:
1.  **C# Condenser:** Write a short, deterministic C# script using `System.Text.Json` to stream the `trace.jsonl` file and extract only the high-level method shapes and arguments into a tiny (~50 KB) summary file.
2.  **LLM Generation:** Pass the condensed summary file to a high-tier LLM to generate the boilerplate BenchmarkDotNet C# code for the E2E tests.
3.  **Execution:** Run the BDN suite in Release mode to generate the final comparative data tables for the thesis.
