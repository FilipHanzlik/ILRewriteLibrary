6. Analysis plan: bounded, evidence-first, reusable instrumentation
-----------------------------------------------------------------
User's concern:
  Many consumers make it hard to determine an expected mix of reads and writes.
  The hypothesis is a tradeoff between cheap access and cheap mutation. User also
  suggested behavior might be selected dynamically.

Resolution:
  Do not seek one universal read/write ratio. Characterize workload shapes and
  determine the conditions under which alternative representations win.

Useful workload families (classification, NOT measured performance rankings):
- Extensive analysis + selective mutation: ILLink.
- Scanning + small edits: resource/attribute cleanup.
- Multiple passes reusing state: macios assembly-preparer.
- Substantial body/member generation: Android marshal wrappers or MAUI XamlC.

Initial focus:
  One ILLink workload family is enough to start. Add one targeted-rewrite pipeline
  later for contrast. Do not integrate the entire inventory first.
  ILLink has broad deployment and large graphs; XamlC is interesting for developer
  build latency. Neither establishes that Cecil dominates their total runtime.

Suggested first research question:
  For selected ILLink workloads, how much time/memory is spent materializing and
  retaining method bodies, how often are they revisited, and how many are modified?

Read/write call counts alone are insufficient:
- First decode versus repeated cached reads.
- Sequential scan versus random access/control-flow work.
- One-operand edit versus full-body replacement.
- Removal before any body read versus removal after analysis.
- Few edited methods spread across many assemblies versus dense local edits.
- Retention across passes versus short-lived temporary representations.
- A small edit can still force substantial serialization.

Suggested staged measurements:
1. Uninstrumented baseline:
   End-to-end elapsed time, CPU, allocation/GC, peak/retained memory, variability.
   Profile before deciding what counters are worth adding.
2. Materialization:
   Body decode events, distinct decoded bodies, decoded IL bytes, instruction
   creation from decoding versus generated instructions, method metadata activity.
3. Reuse:
   Cached body accesses and repeated analysis/pass visits where observable.
   A Body getter call does not prove full instruction enumeration.
4. Mutation:
   Bodies modified/replaced/added/removed, and decoded-but-unmodified bodies.
5. Resolution/output:
   Resolver requests/cache behavior; raw versus decoded writer paths if relevant;
   assembly write/copy behavior and phase costs.

These counters are a proposed progression, not all mandatory in milestone one.
Decoded-but-unmodified is not synonymous with unnecessary analysis.

Instrumentation correctness/overhead:
- Start at meaningful boundaries, not a timer/log record in every tiny getter.
- Prefer aggregated counters; separate diagnostic runs from timing baselines.
- Logging names/ToString/object contents can itself trigger lazy reads.
- Record stable identifiers without forcing extra materialization.
- Tokens are module-scoped; added entities may not yet have output tokens.
- Distinguish event counts from distinct bodies, and materialized from generated
  objects. Define each metric precisely before naming it.
- Avoid a global per-instruction contended counter; instrument at coarser points
  or aggregate appropriately if concurrency is present.
- Inclusive timings overlap; do not sum them as independent phase costs.
- Managed allocated bytes, retained heap, peak working set, and GC pause/CPU are
  different measurements.
- Do not keep strong references to every observed object merely for counters:
  that can change lifetimes and invalidate memory conclusions.

Mutation/phase tracking limitations:
- Collection add/remove hooks miss changes to Instruction.Operand/OpCode, locals,
  EH boundaries, references, flags, and replacement of an entire body.
- Cecil does not inherently know which ILLink phase is executing.
- Existing linker events or optional small diagnostic ILLink hooks may be needed.
  These would be instrumentation only, not a change to trimming logic.
- The earlier preference was to leave ILLink unchanged; do not silently broaden
  scope to modifying ILLink. Try Cecil-only observation first and explain gaps.
- Baseline comparison/snapshots can also materialize otherwise unread state.
  Do not claim exact comprehensive mutation counts until all mutation paths are
  covered and the observation strategy is shown not to alter the workload.

Replay:
- A bounded recording/replay harness may isolate a measured hotspot later.
- It is NOT the first milestone and need not reproduce every Cecil API.
- Capture external/logical requests, not recursively replay all internal calls.
- Match semantic work rather than forcing a new library to expose Cecil objects.
- Replay changes application allocations/object lifetimes and cannot establish
  the same end-to-end speedup as a real ILLink integration.

Possible first deliverable:
  Reproducible report for selected workloads: actual dependency/revisions,
  materialized bodies/IL/instructions, identified allocation/time hotspots,
  and cautiously defined reuse/mutation coverage.

7. Adaptive representation remains a hypothesis, not implementation scope
------------------------------------------------------------------------
Discussed possibility:
  raw body -> lightweight decoding for analysis -> editable representation

Compare eventually:
- Streaming/compact: less retained state, potentially repeated decoding.
- Cached editable bodies: higher allocation, cheaper revisits and mutation.
- Adaptive promotion: start lightweight and materialize when beneficial/required.

Mutation is not the only reason to materialize: repeated analysis, CFG building,
and random access can justify richer cached state.
Automatic promotion has conversion/bookkeeping costs. An explicit per-body/pass
policy might be simpler. No switching threshold or API has been selected.
Unmodified IL can still require token remapping after metadata changes.
Analysis must see effective edits before final emission; keep the earlier
original/current/editor-local view discussion as architectural context only.

PostTrimmingPipeline:
- Preloads assemblies via DirectoryAssemblyResolver with ReadWrite=true.
- Executes obsolete-preserve check, embedded-library stripping, optional resource
  designer removal, abstract-method fixes, optional keep-alives.
- Writes modified assemblies in place, with symbol/deterministic-MVID handling.
- Inner RID build: after ILLink, before ReadyToRun/crossgen2.

AssemblyModifierPipeline:
- Uses AssemblyPipeline and architecture-specific resolver/context state.
- FindJavaObjectsStep -> SaveChangedAssemblyStep -> FindTypeMapObjectsStep.
- Serializes changed assemblies; copies unchanged inputs to destinations.
- Type-map discovery follows saving because saving can change MVID.
- LinkAssembliesNoShrink derives from it, adds steps, then calls base.BuildPipeline.

13. Small standalone C# question covered in this conversation
-------------------------------------------------------------
List<T> can expose its current Count elements as a Span<T> via
System.Runtime.InteropServices.CollectionsMarshal.AsSpan(list), available .NET 5+.
Obtaining it is O(1), no allocation/copy. Ref iteration can modify elements in place,
especially useful for structs. Ordinary iteration gains depend on the workload/JIT.
Do not structurally modify the list or change capacity while using the span;
reallocation can leave it pointing at the old backing array. Existing-element
reads/replacements are different from structural edits.
This was explanation only, not a chosen optimization for Cecil.
